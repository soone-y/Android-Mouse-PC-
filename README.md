# Sensor Mouse Lab v7 — Measurement & Replay

ブラウザ上でスマートフォンの並進運動をIMUから推定するための**測定・検証用アプリ**です。PCのカーソル・Bluetooth HIDは実装していません。外部ライブラリ、サーバーへのセンサーログ送信、APIキーは不要です。既存リポジトリのzlibライセンスに従って利用してください。

## 配置

```
index.html
css/
  styles.css
src/
  math.js           # 3次元ベクトル・クォータニオン
  imu.js            # ジャイロ姿勢推定・重力推定（動作中は補正をゲート）
  stationary.js     # 初期静止パターンと一致するかの判定
  integration.js    # 物理二重積分：自由系列 / ZUPT系列
  pipeline.js       # 生値→姿勢→初期座標系→積分の組み立て
  diagnostics.js    # 記録・CSV/JSON・CSV再生・時間基準比較
  visualization.js  # 描画（物理座標を変更しない）
  app.js            # UIイベント・ブラウザ権限・画面配線
package.json
tests/
  core.test.js
  browser_check.py  # Chromium/Playwrightでの模擬入力テスト
```

**重要：v7から `index.html` 単独では起動しません。** `index.html`, `css/`, `src/` を同じ階層に置き、GitHub Pages の HTTPS か `http://localhost` で開いてください。ESモジュールの読み込み制約のため、`file://` で直接開く方法は推奨しません。GitHub Pagesの場合はリポジトリの公開ディレクトリへ、相対パスを維持して配置します。

## 変更点と設計の方針

1. **純粋積分系列**：入力は初回姿勢基準で回転させた平面加速度 `(m/s²)`。加速度の平滑化・閾値除去・感度・摩擦・速度減衰・実行中の加速度シフト補正を適用しません。台形公式で `v (m/s)` → `x (m)` を求めます。表示倍率の変更は無影響です。
2. **静止補正系列**：まったく同じ入力で別に計算します。`StationaryDetector` が初期静止サンプルに近いセンサーパターンを約450ms確認したときのみ、当該系列の速度を0にします。積分済みの位置は書き換えません。自由系列へはフィードバックしません。
3. **入力ソース比較**：OS提供の `DeviceMotionEvent.acceleration`、および重力込み加速度から独自の姿勢推定で重力を差し引いた推定値を、各々自由系列・静止補正系列に入力します。独自推定の姿勢追跡では、強い並進加速度を重力として誤認しにくいよう、重力方向の補正を条件付きで抑制します。誤認を完全に防ぐものではありません。
4. **センサー時刻の不確実性**：ライブ処理はJavaScriptがイベントを受け取った `performance.now()` を時刻とします。`e.interval` も記録し、CSV再生では両方の時間基準を試します。`e.interval` が各測定の正確なタイムスタンプだと断定できないため、実機側の真の測定時刻の問題は未解決です。
5. **ギャップの扱い**：入力間隔が100msを超えた場合、積分をスキップし、ギャップ件数を記録。速度を勝手にゼロへリセットして誤差を隠しません。これも欠測を補完するものではありません。
6. **座標系**：初回補正時の端末3D座標に戻した加速度のXY成分を積分します。スマホを傾けても平面を固定する意図ですが、ヨー角ドリフトやスマホのセンサー座標と画面の向きの違いは残り得ます。Y反転はあくまで描画側です。

## 操作手順

1. GitHub PagesをスマホのHTTPSで開く。**記録開始** → **センサー開始** → スマホを安定した面に置く → **静止補正（約1.2秒）**。完了メッセージとサンプル件数を確認する。
2. 姿勢を固定した水平移動、持ち上げて移動、回転のみ、停止の4実験を**別々に**行う。物理的な平行移動が目的なら、最初のテストは水平移動10cmを推奨する。
3. `OS加速度 / 静止補正なし` と `OS加速度 / 静止補正あり` を見比べる。OS加速度が取得できないブラウザでは独自重力除去の結果を表示する。
4. 区間の最初と最後で **実測区間の開始/終了** ボタンを使い、任意で実測変位X/Yをcmで入力。ボタンを押す動作そのもののセンサー影響に注意する。
5. 記録停止後CSVまたはJSON保存。新たな実験や再計算では、**既存CSVの再生と比較**でCSVを選択する。

## v6 CSVの再解析

- 推奨の **補正前の平面加速度** は、v7の `anchor_native_x/y`、旧v6の `anchor_a_x/y` などを優先します。
- **従来の補正後加速度** は、旧v6の `corrected_x/y` などを優先します。旧v6の `corrected` には自動調整された `state.shift` が含まれるため、こちらは厳密な未加工の積分比較ではありません。
- **受信時刻系列** と **公称間隔系列** は同じ平面加速度データを積分します。さらに、記録済み `matched` をZUPT条件として適用した系列を比較します。
- CSVが持つ旧v6の `matched` 判定を用いても、それは静止の正解ラベルではありません。リアルな運動軌跡の真値もCSVにはないため、どちらが真の位置に近いかは判定できません。
- v6とv7で姿勢推定アルゴリズム・自動補正が変わるため、v6の平面加速度を取り込む再生は、**姿勢推定そのものの再計算ではありません**。姿勢推定を再検証するには、加速度・ジャイロ・実測を含む新規収録が必要です。

## 技術上の限界（重要）

- 慣性センサーは位置や速度を直接観測しないため、一定のバイアスは位置誤差として時間の2乗で蓄積します。停止中と等速移動中はIMUだけでは区別できません。ZUPTは補助的な仮定です。
- 初期静止パターンは姿勢が変わると一致しにくく、また初期姿勢が同じ等速移動を誤って静止と判定し得ます。
- OSの `acceleration` はハードウェア生値ではなくOS/ブラウザ処理済みの可能性があります。初期姿勢基準のXY平面は、世界に固定された絶対座標系ではありません。
- 加速・減速区間が物理的に釣り合うとしても、センサーのバイアス、短時間の衝撃の取りこぼし、姿勢誤差、時刻の不一致によって積分値は釣り合わないことがあります。
- この実装では磁力計、カメラ、外部基準点、Androidの高精度センサー時刻は使っていません。スマホ実機での運動距離精度は未検証です。

## テスト

```bash
npm test
```

Node.js 22で単位テスト（加速度パルス・積分値・ZUPT分岐・ギャップ検出・重力補正ゲート・CSV再生）を実行できます。

Chromium と Python Playwright があれば、`python tests/browser_check.py` で模擬ブラウザ操作ができます。検証ではページ内部のセキュアコンテキスト設定と `devicemotion` イベントを**合成**しているため、実機の権限や精度を検証するものではありません。

## 推奨する次の実験

同じスマホ、同じ姿勢で、(a)机上を水平に10cm滑らせる、(b)持ち上げて10cm移動して置く、(c)傾けるだけ、(d)元位置への往復、を複数回記録。実測の正味変位、自由系列の終了時速度と位置、ZUPTの発火を比較する。入力の計測限界が卓越すると判断できれば、別の測定手段（カメラによる相対移動推定など）へ移行する根拠とする。
